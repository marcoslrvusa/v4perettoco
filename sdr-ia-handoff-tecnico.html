Todos os clientes usam a mesma espinha dorsal. Mudam o prompt, o CRM, o schema do banco e as regras de qualificação — não o desenho. Entender esse padrão uma vez resolve os oito clientes.

Princípio de projeto

O n8n é stateless entre execuções. Todo estado de conversa vive fora dele — no Supabase (aafbb_leads, aafbb_chat_history) e no Redis (buffer de debounce com TTL curto). Se um nó falha, a próxima mensagem do lead continua de onde parou. Nunca guarde estado em variável de nó esperando que ele sobreviva.

3.6 O que não existe (e deveria)

  • Error workflow global — só o AGF tem. Nos outros, falha é invisível até alguém abrir a lista de execuções.
  • Retry com backoff — nós HTTP e de modelo não têm política de repetição. Um 429 da OpenAI perde a mensagem do lead.
  • Fallback de modelo — se o modelo principal falha, não há secundário.
  • Rate limiting por lead — apenas debounce de 1,2 s; um lead que manda 20 mensagens ainda gera uma chamada por rajada.
  • Testes / ambiente de staging — a instância é única; todo teste é em produção.
  • Versionamento dos JSONs — os arquivos em projetos/sdr-ia/ são snapshots manuais, não a fonte de verdade. A fonte é a instância.

A armadilha do camelCase — causa raiz do follow-up quebrado

O DDL escreve telefoneCliente sem aspas. O Postgres faz fold para minúsculas e a coluna real passa a ser telefonecliente. A API REST devolve telefonecliente. Todo nó que referencia $json.telefoneCliente recebe undefined — e o erro só aparece em runtime, dentro do nó que consome o campo, não na expressão que o produziu.

Regra para o futuro: ou padronize tudo em snake_case desde o DDL, ou cite os identificadores com aspas duplas ("telefoneCliente") em todas as camadas. O estado atual é misto — e é a origem do INC-01 e de metade dos bugs silenciosos da base.

-- histórico de uma conversa

from public.aafbb_chat_history

Ponto cego conhecido: o nó Filtra Tempo do follow-up ignora silenciosamente qualquer lead com last_interaction_at nulo (if (!last) continue;). Lead criado pelo Outbound que nunca mandou mensagem pode ficar eternamente fora da cadência. Verifique com a segunda query acima antes de assumir que “o follow-up está lento”.

4.4 RLS e acesso

As tabelas têm RLS habilitado e nenhuma policy — ou seja, anon não lê nada. Os workflows usam a service role, que ignora RLS. O problema: alguns nós gravam a service/anon key no corpo do próprio nó em vez de usar credencial (seção 08). Se você rotacionar a chave, esses nós quebram sem aviso.

5.2 Ferramenta de linha de comando (n8nac)

O repositório usa n8nac para tratar workflow como código. Antes de qualquer comando, resolva o ambiente ativo — ele é a fonte de verdade do caminho de sync:

npx --yes n8nac push      # envia do repositório para a instância

Antes de rodar push

O ambiente producao-2 aponta para a instância real e a validação nativa está em nível 0 (off): o push valida contra o schema embarcado, que pode divergir do que está rodando. Um push sobrescreve o workflow inteiro — não faz merge. Faça pull antes de qualquer edição e guarde o JSON atual como backup. Se precisar de validação ao vivo, peça a mudança de nível a quem administra o toolchain; não altere por conta própria.

R1 · Verificar a saúde da operação em 5 minutos

R2 · Investigar uma execução que falhou

O padrão é sempre o mesmo: descobrir qual nó falhou, qual expressão estava sendo avaliada e qual dado entrou nele.

  1. Abra Executions e filtre por Error. A coluna “Last Node” já entrega 80% do diagnóstico.
  2. Clique na execução e depois no nó vermelho. A aba Input mostra o JSON que chegou — é ali que está o campo undefined.
  3. Se o erro for de expressão, confira se o nó referenciado existe na versão atual. Renomear nó quebra toda referência $('Nome Antigo') — o erro só aparece em runtime.
  4. Reproduza com pin data: copie o Input do nó com problema, fixe no nó anterior e execute só o trecho.
# erro + nó + descrição de uma execução
curl -s -H "X-N8N-API-KEY: $N8N_KEY" \
  "https://n8n.fvmarketing.com.br/api/v1/executions/<id>?includeData=true" \
  | jq '.data.resultData | {lastNodeExecuted, message: .error.message, node: .error.node.name}'

# quais nós mais falham em um workflow (últimas 100 execuções)
curl -s -H "X-N8N-API-KEY: $N8N_KEY" \
  "https://n8n.fvmarketing.com.br/api/v1/executions?workflowId=fceKFeTBnRfzhfSz&limit=100&includeData=false" \
  | jq -r '.data[] | select(.status=="error") | .id' \
  | while read eid; do
      curl -s -H "X-N8N-API-KEY: $N8N_KEY" \
        "https://n8n.fvmarketing.com.br/api/v1/executions/$eid?includeData=true" \
        | jq -r '.data.resultData.lastNodeExecuted'
    done | sort | uniq -c | sort -rn

Execuções completas expiram conforme a retenção configurada. Se a lista estiver vazia, o problema é retenção — não ausência de erro.

R3 · Puxar, editar e publicar um workflow com segurança

Regra de ouro: a instância é a fonte de verdade, o repositório é o backup. Nunca edite o JSON do repositório e dê push por cima de algo que mudou em produção.

  1. npx --yes n8nac env status --json — confirme o host e o workflowsPath.
  2. Faça uma cópia do estado atual: curl .../workflows/<id> > backup-<data>.json.
  3. npx --yes n8nac pull — traga a versão viva para o repositório.
  4. Edite. Se for mudança de lógica, altere um nó por vez e valide a expressão no painel de output.
  5. npx --yes n8nac push — o push substitui o workflow inteiro.
  6. Abra o workflow na UI, execute uma vez com dado fixado e confira o resultado antes de considerar concluído.

Não faça

Não edite o mesmo workflow em dois lugares (UI e repositório) sem reconciliar. Não rode push com o workflow em execução. Não altere nome de nó existente: as referências $('Nome') são por texto e quebram silenciosamente — prefira adicionar um nó novo e renomear só depois de ajustar todas as referências.

R4 · Alterar o prompt de um agente sem quebrar o fluxo

O prompt vive no nó agent (campo options.systemMessage), não em arquivo. Ele contém variáveis de expressão que precisam continuar existindo.

  1. Mapeie as variáveis antes de editar: {{ $json.formattedHistory }}, {{ $('Monta Mensagens').first().json.messages }}, dados do lead.
  2. Altere o texto, preserve as variáveis. Se precisar de um campo novo, garanta que o nó anterior o produza.
  3. Valide o JSON de saída do qualificador: o Parse Qualificacao faz JSON.parse — uma resposta com markdown quebra o fluxo inteiro.
  4. Rode com 3 conversas de teste: abertura (menu), dúvida e pedido de humano.
  5. Confira o custo: prompts longos + dois agentes por mensagem é o maior item de custo variável da operação.

Sinal de alerta: se após a edição o Parse Qualificacao começar a falhar, o modelo está devolvendo texto fora do JSON. Reforce no system prompt “Retorne SOMENTE o JSON” e reduza a temperatura antes de culpar o código.

R5 · Testar sem mandar mensagem real para o cliente

Não existe sandbox. Testar em produção significa, na prática, controlar onde o fluxo para.

  • Pinned data: fixe a saída do nó Campos Iniciais e execute a partir dali. O caminho até o agente roda de verdade; o envio não.
  • Desabilite o nó de envio: no editor, Deactivate node em Envia Resposta WhatsApp (ou equivalente). O fluxo segue e você inspeciona a saída do agente.
  • Número de teste: use um WhatsApp seu no Campos Iniciais pinado. Nunca use o número de um lead real como cobaia.
  • Follow-up: o disparo é por horário; para testar, ajuste temporariamente fu1_horas para 0 no nó ⚙️ Config Followup e volte ao valor original depois.

Efeito colateral que ninguém lembra

Rodar o workflow de atendimento grava em aafbb_leads e pode criar contato/card no Kommo. Se for só teste de prompt, prefira pin data antes de Normaliza Lead e desative os nós de CRM.

R6 · Instalar o monitor de erros global (faça isso primeiro)

O AGF já tem o padrão pronto: Error Trigger → Montar Evento → Gravar em eventos_operacao. Replique para os demais clientes e você ganha histórico consultável em vez de descoberta tardia.

  1. Crie um workflow novo com nó Error Trigger.
  2. Nó Code: monte um envelope fixo (workflow, execution_id, nível, etapa, mensagem, detalhe). Campos fixos, sem interpretação de linguagem natural.
  3. Nó HTTP Request para o Supabase, com credencial — nunca a chave no corpo do nó (o monitor atual do AGF faz isso; ver seção 08).
  4. No workflow monitorado: Settings → Error Workflow → selecione o monitor. Sem isso o Error Trigger nunca dispara.
  5. O monitor não deve ter error workflow próprio — evita recursão. Se o insert falhar, a falha aparece na execução dele.

Alerta por e-mail não vai funcionar hoje: a instância está com smtpSetup: false (visível em /rest/settings). Enquanto não houver SMTP configurado, use consulta à tabela de eventos ou um webhook para Slack/Telegram. Não prometa alerta por e-mail ao cliente antes de testar.

R9 · Corrigir “Invalid schema” no Supabase (INC-03 e INC-04)

Invalid schema: paludo e Invalid schema: genics significam que o nó aponta para um schema que o PostgREST não reconhece. Não é erro de credencial nem de tabela.

  1. No Supabase, confirme o schema real: select schema_name from information_schema.schemata;.
  2. No nó Supabase, abra Options → Schema. Se o campo estiver vazio, o padrão é public — e a tabela precisa estar lá.
  3. Se o schema existe mas a tabela não, o projeto está incompleto (Paludo): não “conserte” apontando para public por conveniência; crie a estrutura correta.
  4. Rode a migration de referência (projetos/sdr-ia/aafbb/migration.sql) como modelo de DDL.

Paludo é diferente de Genics

Genics é cliente em produção com workflow quebrado — corrigir o schema tende a resolver. Paludo nunca foi configurado: o follow-up está ativo sozinho, sem o workflow principal. Desligar o follow-up do Paludo é a ação correta até o projeto ser retomado; deixá-lo ligado só gera erro recorrente.

R10 · Rotacionar credencial exposta e fazer rollback

Rotação (tokens no corpo do workflow)

  1. Identifique todos os nós que usam o valor: busque pelo prefixo do token no JSON do workflow.
  2. Revogue no provedor (Meta, Supabase, Kommo) antes de editar o n8n — evita janela de uso indevido.
  3. Crie a credencial no n8n e troque os nós para Predefined Credential Type.
  4. Salve, execute um teste real e só então remova o valor antigo do JSON e do histórico do repositório.

Rollback

  • Com histórico de versões habilitado: Workflow → ⋯ → Version history → restaurar a versão anterior à mudança.
  • Sem histórico: restaure o JSON salvo antes da edição (R3, passo 2) e faça push. Guarde o backup com data no nome.
  • Banco: mudanças de schema não têm rollback automático. Antes de qualquer alter table, exporte a tabela ou use uma migration reversível.

Combinado: toda alteração em produção deve ter um JSON de backup nomeado (backup-AAAA-MM-DD-HH.json) no mesmo diretório do workflow. É o único rollback confiável hoje.

08 Segurança e LGPD

Esta seção não é sobre conformidade teórica. É sobre três coisas concretas: credenciais que estão no lugar errado, dados pessoais que ficam guardados para sempre e um canal (WhatsApp) com regras próprias que, se violadas, derrubam o número do cliente.

O achado mais grave: credenciais dentro do workflow

Tokens da Meta, chaves do Supabase e JWTs estão no corpo dos nós, não em credenciais do n8n. Quem tem acesso de leitura ao workflow — ou ao JSON exportado, ou ao repositório — tem a credencial. O caso mais crítico é o monitor do AGF, que grava com a chave anon do Supabase embutida em um nó HTTP.

8.3 Pontos de atenção para o DPO / jurídico

  • Base legal e transparência: o lead precisa saber que fala com uma IA. Os prompts atuais apresentam a assistente pelo nome, mas nem todos declaram explicitamente que é automatizado — validar por cliente.
  • Retenção: aafbb_chat_history cresce sem expurgo. Definir prazo (sugestão: 90 a 180 dias após encerramento) e um job de limpeza. Hoje o dado é eterno por omissão.
  • Operadores e transferência internacional: OpenAI (EUA), Meta (EUA), Supabase (região do projeto — confirmar), Kommo. Precisam constar no contrato/DPA do cliente.
  • Direitos do titular: não existe fluxo para atender exclusão/anonimização sob demanda. Mínimo: uma query de purge documentada por cliente.
  • Minimização: o histórico completo é enviado ao modelo a cada mensagem. Avaliar janela de contexto (últimas N mensagens) — reduz custo e exposição.
  • Logs de execução do n8n: contêm payloads com telefone e conteúdo. A retenção de execuções é uma decisão de segurança, não só de disco.

8.4 Regras do canal WhatsApp

Janela de atendimento de 24 h: fora dela, só é possível iniciar conversa com template aprovado. O Outbound da AAFBB já usa aafbb_boas_vindas — correto. O follow-up usa texto livre (textBody), o que só funciona dentro da janela. Se o FU1 for disparado após 24 h de silêncio, a Meta pode rejeitar a mensagem: é um risco de arquitetura, não só de código.

  • Opt-in: confirme como o número foi coletado (formulário, indicação, evento). O outbound por polling do Kommo pode captar lead sem consentimento explícito para WhatsApp.
  • Opt-out: o fluxo encerra a cadência (stop_followup), mas não há comando de descadastro reconhecido pelo agente. Implementar “pare/sair” como gatilho determinístico.
  • Qualidade do número: bloqueios e denúncias derrubam o quality rating e podem suspender o número do cliente. Follow-up sem resposta é o principal vetor.

11.4 Definição de pronto do handoff

O handoff está concluído quando a nova pessoa consegue, sem ajuda: (1) identificar um workflow com erro em menos de 5 minutos; (2) corrigir uma expressão quebrada e publicar com segurança; (3) explicar por que o follow-up da AAFBB falhava; (4) saber quem acionar quando o problema é de CRM, de Meta ou de infra. Se qualquer uma dessas respostas depender de perguntar, o handoff não terminou.
