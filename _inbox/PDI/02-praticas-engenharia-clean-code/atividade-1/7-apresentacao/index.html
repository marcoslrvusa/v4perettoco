Clean Architecture / ports-adapters / testes

1. Contexto

A FV herda um core legado onde uma mesma classe PedidoService abre conexão com banco, manda e-mail, calcula imposto, gera PDF e escreve log. Tudo num só arquivo de quase 600 linhas. Quando o time precisa mudar a regra de imposto, trava o e-mail; quando ajusta o log, quebra o relatório. É o clássico efeito dominó: nada é isolado.

Analogia do cozinheiro faz-tudo
Imagine um restaurante onde uma única pessoa compra, cozinha, lava a louça, atende e faz a conta. Se ela fica doente, o restaurante fecha inteiro. O SOLID é contratar especialistas: um compra, um cozinha, um lava. Cada um faz bem o seu e o restaurante continua funcionando mesmo se um falta.

2. Diagnóstico

Com classes onipresentes, o tempo para entregar uma feature pequena explode e os bugs se espalham. Cada linha alterada é um risco para funcionalidades não relacionadas. O custo é escondido, mas real: horas de debugging e medo de tocar no código.

Tempo de entrega de feature (dias)
Bugs por release (contagem)
Raiz do problema: classes com múltiplas responsabilidades e acoplamento direto a detalhes (banco, e-mail, PDF). Não há fronteira entre o o quê o negócio pede e como é implementado.

3. Solução

Aplicar os 5 princípios SOLID para virar o código de dentro para fora: o domínio depende de abstrações, e os detalhes (infra) implementam essas abstrações. Isso habilita a Clean Architecture (Entities → Use Cases → Interface Adapters → Frameworks) e o padrão ports & adapters, onde a regra de negócio não sabe se o dado vem de Postgres, Mongo ou um JSON de teste.

SRP — uma classe, um motivo para mudar. Antes uma classe fazia tudo:

# RUIM: uma classe, 5 responsabilidades
class PedidoService:
    def salvar(self, p): ...        # banco
    def enviar_email(self, p): ...  # e-mail
    def calcular_imposto(self, p): ...  # regra
    def gerar_pdf(self, p): ...     # relatorio
    def logar(self, p): ...         # log

Depois, separamos em papéis:

# BOM: cada classe tem uma responsabilidade
class CalculaImposto:           # regra de negocio
    def executar(self, pedido): ...

class PedidoRepository:         # port (interface)
    def salvar(self, pedido): ...

class EnviaEmail:               # adapter de infra
    def enviar(self, destino, corpo): ...

OCP — aberto para extensão, fechado para modificação. Em vez de if tipo == 'PF', usamos polimorfismo:

# BOM: adicionar novo tipo nao mexe no existente
class DescontoStrategy:
    def calcular(self, pedido): raise NotImplementedError
class DescontoPF(DescontoStrategy):
    def calcular(self, p): return p.total * 0.05
class DescontoPJ(DescontoStrategy):
    def calcular(self, p): return p.total * 0.10

LSP — subtipos devem ser substituíveis sem quebrar o programa. ISP — interfaces enxutas (quem usa e-mail não herda salvar/PDF). DIP — o módulo de alto nível depende de abstração, não do banco concreto:

# BOM: use case depende da interface, nao do Postgres
class FinalizaPedido:
    def __init__(self, repo: PedidoRepository):  # DIP
        self.repo = repo
    def executar(self, pedido):
        self.repo.salvar(pedido)  # PostgresRepo ou FakeRepo em teste
