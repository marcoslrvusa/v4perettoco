# Refatoracao de Modulo Legado com SOLID e Clean Architecture

Engenharia de Software

<h2><span class="num">1.</span> Contexto</h2><p>A FV herda um <strong>core legado</strong> onde uma mesma classe <code>PedidoService</code> abre conexão com banco, manda e-mail, calcula imposto, gera PDF e escreve log. Tudo num só arquivo de quase 600 linhas. Quando o time precisa mudar a regra de imposto, trava o e-mail; quando ajusta o log, quebra o relatório. É o clássico <strong>efeito dominó</strong>: nada é isolado.</p><div class="didactic"><div class="didactic-title">Analogia do cozinheiro faz-tudo</div>Imagine um restaurante onde uma única pessoa compra, cozinha, lava a louça, atende e faz a conta. Se ela fica doente, o restaurante fecha inteiro. O SOLID é contratar <strong>especialistas</strong>: um compra, um cozinha, um lava. Cada um faz bem o seu e o restaurante continua funcionando mesmo se um falta.</div><h2><span class="num">2.</span> Diagnóstico</h2><p>Com classes onipresentes, o tempo para entregar uma feature pequena explode e os bugs se espalham. Não há fronteira entre o <em>o quê</em> o negócio pede e <em>como</em> é implementado.</div><h2><span class="num">3.</span> Solução</h2><p>Aplicar os <strong>5 princípios SOLID</strong> para virar o código de dentro para fora: o domínio depende de abstrações, e os detalhes (infra) implementam essas abstrações. Isso habilita a <strong>Clean Architecture</strong> (Entities → Use Cases → Interface Adapters → Frameworks) e o padrão <strong>ports &amp; adapters</strong>, onde a regra de negócio não sabe se o dado vem de Postgres, Mongo ou um JSON de teste.</p><p><strong>SRP</strong> — uma classe, um motivo para mudar. Antes uma classe fazia tudo:</p><pre><code># RUIM: uma classe, 5 responsabilidades
class PedidoService:
    def salvar(self, p): ...        # banco
    def enviar_email(self, p): ...  # e-mail
    def calcular_imposto(self, p): ...  # regra
    def gerar_pdf(self, p): ...     # relatorio
    def logar(self, p): ...         # log</code></pre><p>Depois, separamos em papéis:</p><pre><code># BOM: cada classe tem uma responsabilidade
class CalculaImposto:           # regra de negocio
    def executar(self, pedido): ...

class PedidoRepository:         # port (interface)
    def salvar(self, pedido): ...

class EnviaEmail:               # adapter de infra
    def enviar(self, destino, corpo): ...</code></pre><p><strong>OCP</strong> — aberto para extensão, fechado para modificação. Em vez de <code>if tipo == 'PF'</code>, usamos polimorfismo:</p><pre><code># BOM: adicionar novo tipo nao mexe no existente
class DescontoStrategy:
    def calcular(self, pedido): raise NotImplementedError
class DescontoPF(DescontoStrategy):
    def calcular(self, p): return p.total * 0.05
class DescontoPJ(DescontoStrategy):
    def calcular(self, p): return p.total * 0.10</code></pre><p><strong>LSP</strong> — subtipos devem ser substituíveis sem quebrar o programa. <strong>ISP</strong> — interfaces enxutas (quem usa e-mail não herda salvar/PDF). <strong>DIP</strong> — o módulo de alto nível depende de abstração, não do banco concreto:</p><pre><code># BOM: use case depende da interface, nao do Postgres
class FinalizaPedido:
    def __init__(self, repo: PedidoRepository):  # DIP
        self.repo = repo
    def executar(self, pedido):
        self.repo.salvar(pedido)  # PostgresRepo ou FakeRepo em teste</code></pre><h2><span class="num">4.</span> Como funciona (pipeline)</h2><div class="pipeline"><div class="pipeline-head"><span
