# Mapeamento de Domínios com Domain-Driven Design (DDD)

Engenharia de Software

<h2><span class="num">1.</span> Contexto</h2><p>A FV opera em <strong>múltiplos domínios</strong>: Imobiliário, Saúde, Varejo e Serviços. Hoje o time modela tudo num único modelo de dados gigante, onde alterar um campo de imóvel quebra a regra de agendamento de saúde. O domínio virou um emaranhado onde <strong>todo conceito conhece todo conceito</strong>.</p><div class="didactic"><div class="didactic-title">Analogia do prédio de apartamentos</div>Um condomínio tem moradores, elevadores, portaria e acadêmia. Cada um é um <em>contexto delimitado</em>: a portaria não precisa saber o que você come na cozinha, e a acadêmia não manda na sua conta de luz. Se tentássemos um único manual para tudo, ninguém entenderia nada. DDD é organizar o prédio em <strong>áreas com regras próprias</strong>, que conversam por recados (eventos).</div><h2><span class="num">2.</span> Diagnóstico</h2><p>Sem fronteiras de domínio, mudanças têm efeito cascata e as regras de negócio ficam espalhadas em <em>ifs</em> por todo o código. (Domain-Driven Design)</strong> dividindo o sistema em <strong>bounded contexts</strong> (contextos delimitados), cada um com sua <strong>linguagem ubíqua</strong>: o vocabulário que negócio e código compartilham sem tradução. Dentro de cada contexto modelamos <strong>agregados</strong> (raiz + entidades + value objects com consistência transacional) e comunicamos mudanças via <strong>eventos de domínio</strong>.</p><p>Mapeamento dos contextos da FV:</p><pre><code># Contextos delimitados
Imobiliario   -&gt; Agregado Raiz: Imovel      (Proposta, Visita)
Saude         -&gt; Agregado Raiz: Paciente    (Agendamento, Prontuario)
Varejo        -&gt; Agregado Raiz: Pedido     (Item, Pagamento)
Servicos      -&gt; Agregado Raiz: Ordem       (Execucao, NotaFiscal)</code></pre><p>Agregado garante consistência: só a raiz é referenciada de fora; filhos não têm identidade pública:</p><pre><code>class Pedido:                       # Aggregate Root
    def __init__(self, id):
        self.id = id
        self.itens = []             # entidades internas
        self._eventos = []
    def adicionar(self, produto, qtd):
        self.itens.append(Item(produto, qtd))
        self._eventos.append(PedidoAtualizado(self.id))</code></pre><p>Eventos de domínio desacoplam os contextos: Saúde não chama Imobiliário direto, apenas publica:</p><pre><code>@dataclass
class PedidoPago(DomainEvent):
    pedido_id: str
    total: float

# orquestrador publica; outros contextos reagem
bus.publish(PedidoPago(pedido_id, total))</code></pre><h2><span class="num">4.</span> Como funciona (pipeline)</h2><div class="pipeline"><div class="pipeline-head"><span A meta é igual a 1.</p><pre><code>A = C_tocados / C_dono        meta: A = 1

Exemplo numérico:
  antes  = 5 toques (CRM, Campaign, export, painel, ETL) / 1 dono  => A = 5
  depois = 1 toque  (só CRM publica, os demais reagem)             => A = 1
  ganho  = 12 mudanças/trimestre x 4 toques x 2 h = 96 h/trimestre</code></pre><p>Segunda régua, o <strong>custo transacional do agregado</strong>: tempo de lock somado ao custo de cada operação dentro da transação. Agregado grande não é só feio, é lento e disputa lock com escrita concorrente.</p><pre><code>T_tx = T_lock + soma(T_op) com n operações

n = 3 filhos : T_tx = 4 ms + 3 x 8 ms = 28 ms
n = 12 filhos: T_tx = 4 ms + 12 x 8 ms = 100 ms   (quase 4x pior)</code></pre><p>Terceira régua, a <strong>carga do barramento</strong>, pela lei de Little ($L = \lambda W$): taxa de eventos publicados multiplicada pelo tempo de processamento do consumidor dá a quantidade de eventos simultâneos em cada worker.</p><pre><code>lambda = 40 comandos/s x 1,5 eventos = 60 eventos/s
W      = 25 ms = 0,025 s
L      = 60 x 0,025 = 1,5 eventos simultâneos por worker
com 3 workers: fila media de 4,5 itens, folga para pico de 2x</code></pre><div class="callout"><strong>Capacidade:</strong> enquanto $L$ por worker ficar abaixo da folga de filas, não há por que escalar. Se a fila crescer por 15 minutos (meta), o gargalo é o consumidor, não o produtor.</div><h2><span class="num">10.</span> Modos de falha e runbook</h2><table><tr><th>Sintoma</th><th>Causa raiz</th><th>Detecção</th><th>Mitigação</th><th>Recuperação</th></tr><tr><td>Job noturno falha após migração</td><td>Schema sem dono</td><td>Alerta de ETL</td><td>Schema como código com revisão</td><td>Reverter migração (5 min)</td></tr><tr><td>Consumidor aplica efeito duas vezes</td><td>Sem chave de deduplicação</td><td>efeitos / eventos &gt; Acoplamento não tem fatura no fim do mês, tem retrabalho todo trimestre.</p><h2><span class="num">12.</span> Checklist de domínio</h2><ol><li>Contexto declarado no mapa com raiz de agregado nomeada.</li><li>Glossário versionado, um significado por termo, sem sinônimos pendentes.</li><li>Nenhum import, query ou foreign key cruzando fronteira de contexto.</li><li>Filhos alcançados somente pela raiz; nenhuma entidade filha exposta em endpoint.</li><li>Uma transação altera um agregado e um só.</li><li>Evento com <code>type</code>, <code>aggregate_id</code>, <code>event_id</code> e <code>ts</code>, congelado após publicação.</li><li>Consumidor valida schema e deduplica por <code>event_id</code>.</li><li>Fronteira com payload externo protegida por ACL nomeada.</li><li>Todo PR de regra cita o termo do glossário na descrição.</li><li>Gate de dependência entre contextos verde em CI.</li><li>Casos de borda cobertos: agregado vazio, filho órfão, id nulo, unicode e payload no limite.</li><li>Dono nomeado para o contexto e para cada contrato de evento.</li><li>Runbook de rollback publicado com tempo de recuperação estimado.</li><li>Ampliação de mudança medida no histórico de revisões e perto de 1.</li></ol>
