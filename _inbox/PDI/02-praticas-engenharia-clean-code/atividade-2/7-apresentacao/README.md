# Pipeline de Testes Automatizados (Unit/Integration/E2E) com 80% de Cobertura

Engenharia de Software

<h2><span class="num">1.</span> Contexto</h2><p>Na FV, testes eram manuais e rodados só na véspera do deploy. O resultado: correção de bug gerava novo bug, e ninguém sabia se o sistema continuava funcionando após uma mudança. A confiança no código era baixa e o <strong>medo de deploy</strong> travava a entrega.</p><div class="didactic"><div class="didactic-title">Analogia do cinto de segurança</div>Dirigir sem teste automatizado é como pegar a estrada sem cinto: você até anda, mas basta um solavanco para se machucar. O teste é o cinto que prende o comportamento esperado: se algo mudar, ele avisa antes do acidente. E, como o cinto, só serve se for usado <em>sempre</em>, não só quando lembra.</div><h2><span class="num">2.</span> Diagnóstico</h2><p>Sem suíte automatizada, o tempo de validação cresce com o time e os retornos de bug em produção aumentam. <em>opcional</em>. Não existe <strong>gate objetivo</strong> que impeça uma mudança de baixa qualidade de ir a produção.</div><p>Cadeia causal em quatro níveis: ninguém escrevia teste porque escrever era caro; era caro porque cada teste exigia banco compartilhado preparado à mão; era lento porque não havia distinção entre o que precisa de infraestrutura e o que não precisa; e, sem teto de cobertura, não existia consequência mensurável por piorar. O sintoma final, regressão de prompt em produção, é a ponta dessa cadeia, não a causa. Tratar só o sintoma, pedindo mais cuidado na revisão, mantém a estrutura intacta.</p><h2><span class="num">3.</span> Solução</h2><p>Criar uma <strong>suíte de testes automatizados em 3 camadas</strong> com <code>pytest</code>, coberta por um <strong>gate objetivo de 80%</strong> aplicado no CI. As camadas: <strong>unitário</strong> (regra pura, rápida, sem I/O), <strong>integração</strong> (use case + adapter real, ex.: Postgres em container) e <strong>e2e</strong> (fluxo ponta a ponta via API). O threshold bloqueia o merge se a cobertura cair abaixo de 80%.</p><p>Configuração centralizada em <code>pyproject.toml</code>:</p><pre><code># pyproject.toml
[tool.pytest.ini_options]
addopts = "-q --cov=src --cov-report=term-missing "
          "--cov-fail-under=80"
testpaths = ["tests"]

[tool.coverage.run]
branch = true
source = ["src"]</code></pre><p>A opção <code>branch = true</code> é a decisão mais subestimada da configuração: sem ela, código dentro de um <code>else</code> nunca executado pode passar despercebido. Com o ramo ativado, o denominador passa a ser o par condicional: $C_b = (R_t / R_x) \times 100$, com $R_t$ ramos tomados e $R_x$ ramos existentes. O número cai em relação à medição por linha, corretamente, porque agora ele reflete comportamento não exercitado e não apenas linha visitada.</p><p><strong>Exemplo numérico:</strong> um módulo com $R_x = 40$ ramos condicionais e $R_t = 31$ tomados entrega $77{,}5\%$, abaixo do teto, e o merge é bloqueado. Cobrindo os ramos de erro, $R_t = 34$ e $85\%$ liberam a mudança. A conta é fechada e qualquer um a refaz com o relatório <code>term-missing</code> na mão.</p><p>No CI (GitHub Actions), o passo de teste falha o pipeline se a cobertura for insuficiente:</p><pre><code># .github/workflows/ci.yml
steps:
  - uses: actions/setup-python@v5
    with: { python-version: "3.12" }
  - run: pip install -e .[test]
  - run: pytest        # respeita --cov-fail-under=80</code></pre><p>Exemplo das 3 camadas:</p><pre><code># unitário: regra isolada
def test_calcula_imposto_pf():
    assert CalculaImposto().executar(Pedido(100)) == 5

# integração: use case + repo real (fixture de container)
def test_finaliza_pedido_salva(repo_postgres):
    FinalizaPedido(repo_postgres).executar(Pedido(100))
    assert repo_postgres.buscar(1) is not None

# e2e: fluxo via API
def test_post_pedido_api(client):
    r = client.post('/pedidos', json={'total': 100})
    assert r.status_code == 201</code></pre><h2><span class="num">4.</span> Como funciona (pipeline)</h2><div class="pipeline"><div class="pipeline-head"><span class="pipeline-title">Suíte automatizada com gate 80%</span><span class="pipeline-live"><span class="dot"></span> fluxo em execução</span></div><div class="pipeline-body"><div class="pl-rail"><span class="pl-pulse p1"></span><span class="pl-pulse p2"></span><span class="pl-pulse g"></span></div><div class="pl-steps"><div class="pl-step"><div class="num">1</div><div><div class="name">Configurar <code>pyproject.toml</code></div><div class="desc">Definir <code>--cov-fail-under=80</code> e <code>branch=true</code>.</div><span class="pl-chip"><span class="pl-tag 1">audit</span></span></div></div><div class="pl-step"><div class="num">2</div><div><div class="name">Camada unitária <code>tests/unit/</code></div><div class="desc">Testa regras puras em ms, sem I/O: base da pirâmide.</div><span class="pl-chip"><span class="pl-tag rapido">ok</span></span></div></div><div class="pl-step"><div class="num">3</div><div><div class="name">Camada integração <code>tests/integration/</code></div><div class="desc">Use case + adapter real (Postgres via fixture).</div><span class="pl-chip"><span class="pl-tag precisa container">warn</span></span></div></div><div class="pl-step"><div class="num">4</div><div><div class="name">Camada e2e <code>tests/e2e/</code></div><div class="desc">Fluxo ponta a ponta pela API de verdade.</div><span class="pl-chip"><span class="pl-tag lento">warn</span></span></div></div><div class="pl-step"><div class="num">5</div><div><div class="name">Gate no CI <code>pytest</code></div><div class="desc">Falha o merge se cobertura &lt; 80% ou qualquer teste vermelho.</div><span class="pl-chip"><span class="pl-tag bloqueia">ok</span></span></div></div></div><div class="pl-footer"><span>Cobertura baixa em novo arquivo = PR bloqueado. A qualidade vira critério de merge, não opinião.</span></div></div></div><h2><span class="num">5.</span> Antes vs Depois</h2><table><tr><th>Cenário</th><th>Antes (manual)</th><th>Depois (gate 80%)</th></tr><tr><td>Validação de release</td><td>Dias de QA manual</td><td>Minutos no CI</td></tr><tr><td>Defeito em produção</td><td>Comum</td><td>Raro (e2e pega)</td></tr><tr><td>Cobertura conhecida</td><td>Desconhecida</td><td>Medida e bloqueante</td></tr><tr><td>Confiança no deploy</td><td>Baixa</td><td>Alta</td></tr></table><p><strong>Exemplo numérico de tempo (parâmetros declarados):</strong> camada unitária de 90 s, integração de 60 s e E2E de 120 s. Em série, o total de 270 s estoura o orçamento de 180 s. Com dois processos na camada rápida, $45 + 30 = 75$ s no caminho crítico, e o E2E roda em estágio separado, some apenas quando executa. O gate fica 105 s abaixo do orçamento, folga suficiente para absorver crescimento da suíte sem virar fila de espera no CI.</p><p>A segunda diferença é a natureza do critério: antes, a validação era uma opinião humana sobre risco; depois, é um número com janela de medição e ação definida para quando estoura. Opinião não bloqueia merge, número bloqueia.</p><h2><span class="num">6.</span> Entregas</h2><ul><li><strong>Config</strong> <code>pyproject.toml</code>: addopts com <code>--cov-fail-under=80</code> e branch.</li><li><strong>Pastas</strong> <code>tests/unit</code>, <code>tests/integration</code>, <code>tests/e2e</code> com exemplos reais.</li><li><strong>Workflow</strong> <code>ci.yml</code>: passo de <code>pytest</code> como gate de merge.</li><li><strong>Doc</strong> <code>TESTING.md</code>: como rodar cada camada localmente.</li><li><strong>Standard</strong> <code>TEST-STRATEGY.md</code>: escopo, termos, tabela de decisão, anti-padrões, telemetria e checklist de adesão de 15 itens.</li><li><strong>Roteiro de demo</strong> <code>DEMO-SCRIPT.md</code>: 20 passos com comando, saída esperada, critério de falha e rollback.</li><li><strong>Roteiro de domínio</strong> <code>ROTEIRO-DOMINIO.md</code>: 15 perguntas de defesa com respostas desenvolvidas.</li></ul><p>Cada entrega tem um artefato de prova: o gate se prova com o <code>pytest.ini</code> versionado, a camada rápida com os arquivos <code>test_*.py</code>, o pipeline com o <code>ci.yml</code> e a regra com o standard. tempo do gate, unit mais integração, abaixo de 3 min, medido na mediana semanal; taxa de teste instável abaixo de 1%, calculada como falha seguida de sucesso sem mudança de código, sobre o total de execuções da semana.</p><table><tr><th>SLI</th><th>Meta</th><th>Janela</th><th>Ao estourar</th></tr><tr><td>Cobertura global</td><td>&ge; Falso negativo, isto é, defeito aprovado pelo gate, não tem orçamento e é endereçado por mutation testing nos módulos núcleo, que mede se o teste falharia se o código mudasse.</p><h2><span class="num">8.</span> Status final</h2><p><span class="status st-warn">NÃO publicado</span>: Desenvolvido e em homologação. Aguarda revisão antes de produção.</p><p><strong>Operação e recuperação.</strong> Checagem diária: abrir o último run do job de teste e confirmar verde. Suspeita de teste instável: reexecutar uma vez sem mudar código; falhou de novo é defeito, passou é instabilidade e vira item de correção. Gate estourado no pull request: rodar <code>pytest --cov=src --cov-report=term-missing</code> localmente, ler a lista <code>Missing</code>, escrever os testes e reenviar, nunca rebaixar o teto. Suíte lenta: <code>pytest --durations=10</code> antes de qualquer paralelismo. Rollback do gate: reverter o commit que alterou a configuração, no mesmo caminho de aprovação de qualquer outra mudança.</p><p><strong>Próximos passos:</strong> E2E nos fluxos críticos que movem dinheiro, mutation testing nos módulos núcleo e sustentação do teto por 12 semanas consecutivas (meta), com leitura semanal das três métricas e registro das exceções em decisão, não em conversa paralela.</p>
