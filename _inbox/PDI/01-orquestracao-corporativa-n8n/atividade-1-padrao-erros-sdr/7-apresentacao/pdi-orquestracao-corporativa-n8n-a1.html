1. Contexto

A operação de Automação & Infraestrutura da V4 Company mantém 10 workflows críticos em produção no n8n: 7 workflows de SDR IA (atendimento inteligente de leads) e 3 workflows de Command Center (monitoramento e orquestração da instância).

Em meados de junho de 2026, identificamos um padrão recorrente: todos os 7 workflows SDR IA apresentavam falhas silenciosas. Erros aconteciam, os workflows paravam ou degradavam, e ninguém era notificado. Algumas falhas passavam dias sem detecção, impactando diretamente o SLA de atendimento aos leads.

Este relatório documenta o PDI (Padrão Universal de Tratamento de Erros) implementado para resolver esse problema de raiz — não apenas corrigindo as falhas pontuais, mas estabelecendo um padrão enterprise reutilizável para todos os workflows da operação.

2.3 Causa Raiz

Ausência de padronização: cada workflow tratava erro do seu jeito improvisado — ou simplesmente não tratava. Não havia taxonomia de erros, política de retry, notificação, persistência ou proteção contra cascata. O resultado era um ecossistema frágil onde uma falha em um nó poderia derrubar todo o fluxo sem deixar rastro.

3. Arquitetura da Solução

Três camadas obrigatórias e complementares. Não são alternativas — um workflow enterprise precisa das três.

Camada 1
Node-Level · Auto-cura local
retryOnFail + continueErrorOutput em cada nó falível. Captura ~73% das falhas transientes (429, 503, timeout) no próprio nó — sem overhead de workflow externo.
~73%
Camada 2
Error Handler Central · Rede de segurança
Workflow único que captura tudo que escapar da Camada 1. Classifica severidade por taxonomia, notifica Slack em < 1 min, persiste na Dead Letter Queue. 10 nós, validado com n8nac.
10 nós
Camada 3
Circuit Breaker + Dead Letter Queue · Proteção sistêmica
Circuit breaker evita sobrecarga em APIs fragilizadas (abre após 5 falhas consecutivas, cooldown de 5 min, recovery automático). DLQ preserva payload completo para replay e auditoria.
2 wf

O que a Camada 1 não cura, a 2 classifica. O que a 2 classifica, a 3 protege e preserva.

3.1 Racional de Design

Por que não um error handler por workflow? Duplicação de lógica. Manter N workflows de erro idênticos é custoso e propenso a dessincronia. Um handler centralizado reduz a superfície de manutenção a um único ponto.

Por que 3 camadas e não 2? A Camada 1 (node-level) é a mais barata e captura a maioria dos casos — mas não cobre erros de lógica (dado inválido, runtime). A Camada 2 classifica o que escapar, mas não protege APIs contra cascata. A Camada 3 existe exatamente para isso: impedir que uma API falha receba golpes em sequência.

E se o Error Handler Central cair? Os erros ficam no log interno do n8n até o handler voltar. Há perda de notificação, mas não de dado — a DLQ é populada no Supabase, que tem SLA próprio. Além disso, o Circuit Breaker Monitor roda independentemente a cada 5 min.

5.1 Código de Classificação

O Code node do Error Handler Central implementa a taxonomia via regex. Abaixo, o core da lógica:

// Error Handler Central — Parse + Classify
const msg = (execution.error?.message || '').toLowerCase();

let errorClass = 'unknown';
let severity = 'info';

if (/5\d{2}|internal server error|upstream/.test(msg)) {
  errorClass = 'server_error'; severity = 'critical';
} else if (/429|rate limit|too many/.test(msg)) {
  errorClass = 'rate_limit'; severity = 'warning';
} else if (/timeout|etimedout|econnrefused/.test(msg)) {
  errorClass = 'timeout'; severity = 'critical';
} else if (/undefined|cannot read|null|not-null/.test(msg)) {
  errorClass = 'data_validation'; severity = 'warning';
} else if (/task runner|disconnect/.test(msg)) {
  errorClass = 'runtime'; severity = 'critical';
}

return [{
  json: {
    correlationId: [workflow.id, execution.id].join('-'),
    severity, errorClass,
    workflowName: workflow.name,
    failedNode: execution.lastNodeExecuted,
    errorMessage: (error.message || '').substring(0, 500),
    executionId: execution.id,
    timestamp: new Date().toISOString()
  }
}];

6.1 Backoff com Jitter

Para falhas persistentes (429, 5xx), usar loop customizado com backoff exponencial:

// Fórmula: min(maxDelay, baseDelay × 2^(attempt-1)) ± 25%
waitSeconds = Math.min(300, 5 * Math.pow(2, attempt - 1)) * (0.75 + Math.random() * 0.5);

10. Anti-Patterns

Erros reais observados nos workflows SDR IA que o padrão veio eliminar.

onError sem main[1]

Erro descartado silenciosamente. O nó falha, mas ninguém vê. Sempre usar onError: "continueErrorOutput" + segundo output conectado ao handler.

Retentar 4xx

Queima API credits à toa. Erro do cliente (400, 401, 403, 404) não vai mudar na próxima tentativa. Só retentar 5xx / timeout / DNS.

200 no erro

Se a resposta é 200 mas houve falha interna, quem chamou nunca sabe. Propagar status HTTP correto.

Error workflow no mesmo canal

Se o workflow de erro usa o mesmo Slack que o principal, uma falha no Slack cria recursão infinita. Usar canais separados.

Não publicar o error handler

Código antigo rodando mesmo depois de "corrigido". Sempre publish (Shift+P) após configurar ou alterar.

Payload sem correlationId

Sem um ID estável entre retries, não é possível ligar uma falha à sua causa original. O correlationId é obrigatório.
