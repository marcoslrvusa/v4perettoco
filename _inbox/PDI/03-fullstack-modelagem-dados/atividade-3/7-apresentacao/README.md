# Arquitetura Serverless para Processamento Assincrono (event-driven)

Arquitetura Full Stack

<h2><span class="num">1.</span> Contexto</h2>

<p>A FV roda alguns jobs de processamento em servidores dedicados 24/7, mesmo quando não há nada a fazer. Paga máquina ociosa à noite, fim de semana e feriado. Para picos, ou sobre-dimensiona (caro) ou fica sem capacidade (lento). O modelo <strong>serverless</strong> inverte isso: você paga só pela execução.</p>

<div class="didactic"><div class="didactic-title">Analogia da lancha por hora</div>Um servidor dedicado é como alugar uma lancha o mês todo: paga mesmo parada no cais. Serverless é pagar só pelos minutos em que a lancha está <em>efetivamente navegando</em>. Se ninguém usa, custo zero. Se 100 pessoas usam ao mesmo tempo, o serviço cria 100 lanchas pequenas sozinho — e some com elas quando o mar esvazia.</div>

<h2><span class="num">2.</span> Diagnóstico</h2>

<p>Servidores ociosos consomem orçamento sem entregar valor. Picos não previstos geram timeouts. O provisionamento manual é lento e errante: ou sobra recurso (dinheiro jogado fora) ou falta (SLA estourado).</p>

<div class="callout"><strong>Raiz do problema:</strong> capacidade é fixa (provisionada por adivinhação), então o custo é pago mesmo sem uso e o pico quebra o teto. Serverless troca capacidade fixa por capacidade elástica e cobrança por execução.</div>

<h2><span class="num">3.</span> Solução</h2>

<p>Migrar jobs esporádicos e APIs de baixo/médio tráfego para <strong>functions serverless</strong> com <strong>auto-scale</strong> a partir de zero. Cobrança <strong>pay-per-use</strong> (por ms de execução + memória). O trade-off é o <strong>cold start</strong>: a primeira chamada após ociosidade leva mais tempo, mitigável com keep-warm estratégico ou tamanho de memória adequado.</p>
